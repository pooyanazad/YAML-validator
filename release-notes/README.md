# Releasing and writing highlights

## Publish a new version

1. Update `__version__` in `yaml_validator/__init__.py` to a new `X.Y.Z`. Starting with 3.5.0, this is the version used for Python, Docker, and GitHub releases.
2. Add reviewed highlights to `release-notes/vX.Y.Z.md` (or a full dated tag filename). Start with the exact preceding tag marker, then describe only changes shipped since it. Merge the version, code, and notes into `main` after CI passes.
3. In **Actions → Docker Build and Push → Run workflow**, select **main**. Leave `manual_tag` empty to use `vX.Y.Z-YYYYMMDD` with today's UTC date. A supplied tag must match the package version.
4. Wait for Docker/GitHub publication, then check **Release & Publish to PyPI** separately. The first workflow automatically dispatches this second workflow. A successful dispatch alone is not proof of a successful PyPI upload.
5. Merge the generated README update PR. If GitHub Actions cannot open it, the summary links the pushed branch so you can open a PR yourself. For bot-created PRs, close and reopen the PR with your own account to start the required CI checks: events generated by `GITHUB_TOKEN` do not normally start another workflow.

PyPI Trusted Publishing must authorize owner `pooyanazad`, repository `YAML-validator`, workflow filename `release.yml`, and environment `pypi`. If the project does not yet exist, configure a pending publisher for project `yamlguard`. These account settings cannot be created by committing workflow code. See [PyPI's setup instructions](https://docs.pypi.org/trusted-publishers/creating-a-project-through-oidc/).

Repository setting **Settings → Actions → General → Workflow permissions → Allow GitHub Actions to create and approve pull requests** allows automatic README PR creation. It does not make the bot approve its own PR or remove branch rules. Without it, create the README PR manually from the summary link. Keep the existing branch protections and admin bypass.

Monthly scheduled runs create a release only when the source package version is new. If that version already has a GitHub release, they refresh Docker `latest` only. New releases also check PyPI before publishing Docker or GitHub. A manual new-release attempt using an already released package version fails with instructions instead of inventing another minor version. Versioned Docker tags from another/unknown commit cannot be overwritten; a retry can reuse a complete two-platform image from the same commit.

## Retry or repair an existing release

| Workflow | When to run it | What it changes |
| --- | --- | --- |
| Docker Build and Push | Publish a new version after its PR is merged | Versioned Docker image + `latest`, GitHub release, README update branch/PR; dispatches PyPI |
| Release & Publish to PyPI | Retry a failed PyPI publication using its existing GitHub release tag | Tests and builds that tagged source, regenerates its packaged README, uploads to PyPI |
| Refresh Release Notes | Correct the text of an existing GitHub release | GitHub description only |

**Refresh Release Notes is not a step in publishing 3.5.0.** To repair the old 3.4.0 description, run it on `main` with `tag=v3.4.0-20261011`. It does not change README, move tags, rebuild Docker, or replace PyPI files.

For a failed PyPI run, fix the reported account/environment issue, then run **Release & Publish to PyPI** on `main` with the existing full release tag. The workflow requires an existing published GitHub release and matching tag/package version. An already published PyPI version is left unchanged; network/server failures are errors, not evidence that a version is unpublished. Inspect PyPI manually if an earlier upload was incomplete: retries do not silently replace or finish an existing version.

## Write accurate highlights

```markdown
<!-- previous-tag: v3.4.0-20261011 -->
- Describe a user-visible change shipped since that tag.
```

A full dated filename takes precedence over the `vX.Y.Z.md` fallback. The marker must match the preceding version tag reachable from the released commit. The generator excludes the current tag on retries and rejects a missing/unrelated base or a current tag pointing at another commit.

Without curated highlights, the generator reports factual category counts from commit subjects and links the complete range; it does not invent features. Existing capabilities belong in usage documentation. GitHub includes grouped commits in a collapsed section. The README contains a short summary and comparison link; its marked block is replaced each time, rather than appending duplicate sections. The PyPI build regenerates that block before packaging, using the same generator and range.

Preview locally without publishing (after the source version is updated):

```bash
python -m scripts.release_notes --version v3.5.0-20261011 \
  --head HEAD --output release-body.md
```
